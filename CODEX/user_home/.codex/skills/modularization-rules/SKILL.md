# Modularization Rules

## 基本方針

- テスト工数は運用コストの支配要因。境界は再テスト負荷の最小化を目的に引く。
- 抽象化の根拠は測定可能な運用利得のみ。「設計の美しさ」は根拠にしない。
- 分離コスト（ファイル +1、import +1、学習 +alpha）は有限。根拠なき分離は負債。
- 同じ要件を満たすなら、モジュール数、レイヤー数、interface数、registry数、転送回数が少ない方を選ぶ。

## 所有者と正本の境界

- 変更前に、振る舞いの所有リポジトリ／モジュールと唯一の正本を特定する。カタログ、複製、生成物、稼働設定、CLI、Viewer、互換シムを、参照・配備・表示の役割だけで正本と誤認しない。
- `ソース → ビルド成果物 → 配備／稼働設定 → 実行時の経路`を時点と責務で分離する。モジュール間契約の所有者は一つに固定し、他モジュールは参照／アダプターに留める。
- 入力が正しく出力が初めて壊れる境界を修正対象にし、下流の修正で症状を隠さない。

## 上から下へ読める構造

- 主要フローは`entrypoint -> orchestration/use case -> domain decision -> adapter/store`の順で一方向に追跡できるようにする。
- 実行時の主要経路は`入口→所有者→ゲートウェイ→バックエンド／ストア→戻り→利用者に見える結果`で追跡し、各境界の入力、判断、出力、次の責任者、失敗契約を示す。意味を理解するためにファイル間を往復させない。
- 上位層が下位層を選び、下位層は上位層のworkflowを知らない。横断registryやcallbackで実行順序を隠さない。
- ユースケースを上から下へ一度読んで、責務、データ変換、失敗境界を説明できない構造は不合格とする。
- 循環依存、相互callback、同等レイヤー間の数珠つなぎ、単なる中継wrapperが必要なら、分割ではなく統合を先に検討する。

## 分離を正当化する3つの根拠

いずれか1つ以上を明示できるときに分離する。

### 根拠1: 再利用（2+ callers）

- 今日2箇所以上から使われていれば切り出す。
- 「そのうち使うかも」は不可（YAGNI）。

### 根拠2: 変更隔離（blast-radius containment）

- 大きな安定モジュール内に「将来独立に変わる見込みの1箇所」があれば、1 caller でも切り出す。
- 変更時に周囲の再テストを省略できるなら、分離コストは回収できる。
- 例: 外部 API のセレクタ/フィールド名、UA、エンドポイント定数、フィーチャーフラグ、モック差し替え境界。

### 根拠3: 純粋ロジックのテスタビリティ

- I/O を伴う orchestrator から純粋関数を抽出し、単体テスト可能にする。
- 2+ callers がなくても妥当。

## 正当化されない分離

- 「concerns が違う」だけを理由とする分離
- 起きていない仮説への先行対応（Protocol / registry / DI / version 切替）
- 物理的に割るだけで callers も isolation も変わらない分離
- clean architecture の形式論のみに基づく階層化

## 判断手順

1. 今日 2+ callers があるか
2. 将来変わる見込みの「1箇所」を周囲の再テストから守りたいか
3. 純粋ロジックを I/O から切り離してテスト可能にしたいか
4. 分離後も主要ユースケースを上から下へ一方向に追跡できるか

1〜3のいずれかがYesで、4もYesなら分離候補。4がNoなら分離方法を変えるか統合する。1〜3が全てNoなら埋め込んだままにする。

局所試験、ヘルスチェック、バックエンド単独の成功を全経路の証明にしない。分離を採用する場合は、各境界の試験と入口からの契約試験を受け入れ基準に含める。

## 提案時に明示する項目

- 分離対象（ファイル / 関数 / 定数）
- 該当根拠（1/2/3、複数可）とその具体
- 根拠1: callers の列挙
- 根拠2: 想定変更の種類・頻度・影響範囲
- 根拠3: テスト可能になる振る舞い
- 分離コスト（追加ファイル数、影響 import 本数）

## 既存モジュールの再評価

- callers が1に減り変更も止まったら統合検討
- 埋め込み部分の変更頻度が上がったら切り出し検討
- 変更のたびに「根拠2で切り出すべきだったか」を自問する
